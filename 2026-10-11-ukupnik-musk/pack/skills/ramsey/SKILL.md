# Ramsey - прожарка отчётов и кода

Предпубликационная прожарка технических отчётов и кода в роли строгого приёмщика.
Имя взято из поп-культуры: персонаж, который приходит на чужую кухню, показывает
дефект конкретным местом, а не абстрактно, и требует переделки. Вердикт без
переделки его не интересует, ровно как список атак без минимального фикса.

Ищет места, за которые зацепится строгий проверяющий, и формулирует минимальные
фиксы. Не редактирует текст сам: выдаёт список атак и патчей на решение инженера.
Диспетчер прожарочных скиллов - см. Routing ниже.

## When to Use

- Перед отправкой отчёта заказчику или архитектору: замеры, миграции, отчёты
- Промежуточные срезы и инцидент-репорты с числами
- Перед публикацией документа, который уйдёт широкому читателю
- Код-прожарка: маршрутизировать в профильные скиллы (см. Routing)

## Routing (диспетчер)

Только скиллы этого пака. Ссылок на внешние скиллы нет намеренно: получатель
пака может не иметь ничего, кроме нативных 58 скиллов Hermes.

| Цель | Скилл |
|---|---|
| Базовые правила текста отчёта (дословные претензии ревью, смешение темпов, самоссылки на wiki) | этот скилл, чек-лист атак ниже |
| План до начала работы, bite-sized шаги | `plan-then-do` |
| Принципы проектирования, ревью, отладки | `pstack-principles` |
| Самодельное решение в отчёте: скрипт, коннектор, обходчик | `research-before-build`: два существующих решения до строчки кода, иначе это велосипед |
| Дисциплина скепсиса к решению, адверсариал в свежем контексте | `agent-skills-doubt-driven-development` |
| Финальная текстовая зачистка AI-слопа | нативный `humanizer` из состава Hermes (58 скиллов поставляются с агентом) |

Don't use for: обычный код-ревью без прожарки (см. нативный `requesting-code-review`), тексты без цифр и выводов.

## Procedure

1. Прочитать отчёт целиком через `read_file`. Составить карту заявлений: каждый вывод и число, от которых он зависит.
2. Прогнать чек-лист атак (ниже). По каждому попаданию зафиксировать: раздел, формулировку атаки, минимальный фикс.
3. Машинная сверка: одни и те же числа и термины во всех разделах (поиск по числу через `search_files`). Расхождение одного параметра между разделами - высший приоритет. Если в документе есть формула расчёта («как считается», методика оценки) - воспроизвести по ней каждую итоговую цифру кодом, а не в голове; расхождение формулы с собственным итогом документа - вопрос на первой приёмке, раньше любых слайдов.
4. Статусы связанных задач - живым запросом в трекере, не по памяти отчёта; дату сверки внести в отчёт.
5. Заявления о состоянии живых систем (порты, сервисы, сертификаты, бэкап-джобы,
   «установлено/не установлено») верифицировать ПРОБАМИ по земле до выдачи списка,
   а не оговорками в тексте: ответ хоста при закрытом порте сервиса («пингуется, порт
   закрыт») - это не «хост лежит»; «бэкапов нет» проверять по конфигу джобы, а не по
   отсутствию упоминания; «не установлено» - пробой характерных портов, а не
   отсутствием в документации. Числа-доли («половина машин») - только из полного
   обхода, не из выборки: «6 из 12 проверенных» вызывает вопрос «а их сколько всего?»,
   полный обход без остатка - нет. Лог всех проб с датой сохранять рядом с черновиком.
   Прожарку текстов, зависящих от тредов трекера или чужих файлов, НЕ завершать без
   перечитывания живых тредов: черновик мог устареть (вопрос уже задан, задачавзята на
   себя, ответ уже получен) - дубль или противоречие в отправленном тексте дороже
   любой атаки из чек-листа.
6. Выдать список: пункт -> раздел -> формулировка атаки -> минимальный фикс. Фиксы применять только после решения инженера.

## Чек-лист атак

1. **Валидность сравнения**: сравниваются ли версии на конфигурациях, одна из которых несёт самодельные патчи? Сравнение на разных конфигурациях невалидно.
2. **Незавершённое как завершённое**: «финальный», «завершена», «итоговый» при незакрытых фазах; противоречие с ранее опубликованными цифрами без публичной корректировки.
3. **Математика остатков**: достижим ли каждый элемент остатка? Если часть объектов физически не существует, ETA по ним фикция - нужна пометка «условно».
4. **Внутреннее противоречие темпа**: «тяжёлые сегменты впереди» + линейный ETA = заниженный срок; должна быть оговорка о линейности и контроле.
5. **Отчёт vs собственные артефакты**: «срабатываний не было» сверять с инцидент-файлами и логами; расхождение трактуется как умолчание.
6. **«Сопоставимо» без доказательства**: двукратные разрывы рядом со словом «сопоставимо» - требовать атрибуцию причины или убрать слово.
7. **Двойные числа**: один параметр - разные значения в разных разделах (окна усреднения, объёмы RAM/диска, проценты).
8. **Статистическая база**: вывод по одной паре точек, разные окна сравнения, отсутствие погрешности.
9. **Физика аномалий**: аномалия при запасе ресурса, интервал тик-событие, нерасшифрованные имена процессов.
10. **Хронология зависимостей**: применено раньше, чем закрыта задача-источник; чей бинарник, md5, привязка к ревизии.
11. **Срезовая метрика как достижение**: err=0 на срезе при остановках в периоде - требовать пометки «срезовая метрика» и ссылки на остановки.
12. **Неотвеченная цель задачи**: заявленная цель не закрыта - документ не может называться финальным.
13. **Грабли в happy-path документации**: если грабли обойдены, всё работает и есть инструкция как делать правильно, разделы «грабли», «попытки», «провалы», «откаты» в документации (README, runbook, инструкция) запрещены. Это внутренний опыт для скиллов и вики, не для артефакта. Документ ведёт по успешному пути; каждый пункт проверять вопросом «это шаг инструкции или история неудач?».
14. **Секция без адресата**: каждый раздел/файл проверять вопросами «кто это читает?», «что читатель должен сделать после?». Обоснование уже принятого решения в артефакте не живёт: решение зафиксировано одной строкой, обоснование - чат/задача. Краткость важнее полноты.
15. **Дубль вместо одного источника**: одна вещь описана в одном месте, остальные ссылаются. Перед созданием файла проверить: есть ли уже файл, где эта информация живёт (README против runbook, чек-лист против задачи). Второй источник с той же информацией = дефект, который разъедется при первой правке.
16. **Устаревший попутчик**: документ хранит открытые вопросы, на которые ответ уже получен. Перед выдачей: каждый открытый вопрос проверять «ответ на него уже был?», был - перенести в зафиксированные вводные и пропатчить зависимые формулировки.
17. **Приближение, одетое как факт**: числа из уст автора с оговоркой «если не путаю», «примерно» вносятся в артефакт без пометки и всплывают на приёмке. Пометка «уточняется инвентаризацией/актом» обязательна.
18. **Проверяемое, не проверенное**: утверждение о доступности в документе для широкого читателя должно быть проверено живой пробой ДО публикации, а не помечено «не проверено». Честная пометка снимает личную ответственность, но не репутационный риск: непроверенное для массового читателя равно ложь. Проверил - запиши дату и метод пробы в текст или verify-log рядом.
19. **Шаблонный антитезис и афоризм-ритм**: одна риторическая конструкция «не X, а Y» повторяется в нескольких разделах, каждый блок кончается афоризмом-подписью, парцеляции по два слова. Это ритм генерации, не автора; проверяющий считывает его как слоп и дальше не верит и цифрам. Считать вхождения конструкции по документу; сильнейший антитезис оставить один, остальные переписать прямыми утверждениями, афоризмы заменить проверяемым фактом блока. Особенно для питчей: там риторика заменяет цифры, и слоп-ритм виден раньше арифметики.

## Persona

Роль - строгий приёмщик (персонаж поп-культуры, не реальный человек): придирчив,
ищет повод вернуть артефакт. Правила игры:

- Атаковать документ, не инженера: каждая атака - проверяемое место текста, не личное качество.
- Атаки формулировать его голосом (резко, коротко), фиксы - нейтральным голосом документа.
- Имена реальных людей - только в диалоге с инженером, никогда в тексте документа.
- Имя приёмщика в тексте документа не упоминается никогда.

## Применение к внешним документам (не только отчётам)

Приёмщик применяется и к инструкциям и рунбукам, которые уходят широкому кругу
читателей (INSTALL, публичные гайды), и к внешним питчам и презентациям (PDF,
слайды), а не только к внутренним отчётам. Мера прожарки для рунбуков -
репутационный риск при прямой лжи: каждое проверяемое утверждение проверяется
пробой, а не помечается честным «не проверено». Мера для питчей - первые пять
атак по приоритету P0/P1: слоп-ритм (атака 19), невоспроизводимая экономика,
двойные числа и противоречие сроков между слайдами проверяющий ловит раньше
описания продукта.

## Защита в тексте (что должно быть заранее)

- Вмешательства в продукт - со ссылкой на согласование (кто, когда).
- Контрольная (нетронутая) конфигурация явно названа.
- Промежуточный статус - в первых строках документа при незакрытых фазах.
- Ограничение методики - у места использования результата, не в отдельной «исповеди».
- Расхождения очередь/факт - пометка «условно» у зависимых расчётов.
- Нулевые метрики - с контекстом периода, не как достижение.

## Pitfalls

- Не превращать ревью в самобичевание: фиксы формулируются нейтрально, без истории ошибок и оправданий. Ответы на незаданные вопросы - такой же дефект, как дыра в цифрах.
- Атаки привязывать к конкретной строке документа; не выдумывать претензии по отсутствующим данным.
- После правок - повторный прогон: фикс одной атаки не должен создавать другую.

## PRISM-проход (второй, после атак чек-листа)

По каждому разделу документа - 2-4 риска или слепых пятна по осям с оценкой Impact/Likelihood:

- Performance / Reliability - подтвердить ли выводы замерами другой длительности
- Isolation / Reputation - не переносится ли дефект на смежные продукты без оснований
- Security / Privacy - утечки имён, IP, паролей, внутренних доменов
- Operability / Monitoring - воспроизводимы ли наблюдения после документа
- Compliance / Legal - сертифицированный контур, самописный код, договорные обязательства
- Maintainability / Scaling - воспроизводимость замера на другом объёме

Пересекающиеся находки чек-листа и PRISM - приоритизировать P0/P1/P2.
Премортем-фрейм: "документ опубликован, через неделю негатив - откуда?" - 3-4
реалистичных источника, на каждый ответ или признание в фиксах.

## Verification

- Каждая атака чек-листа имеет вердикт «выдерживает» или «фикс применён».
- PRISM-проход пройден: по каждой из 6 осей есть вердикт или находка.
- Машинная сверка чисел между разделами - 0 расхождений.
- Статусы задач подтверждены живым запросом, дата сверки в документе.
- Типографика: 0 эм-дашей, 0 ёлочек; AI-штампов нет.
- Заявления о живых системах имеют пробу в логе верификации (дата + метод).
