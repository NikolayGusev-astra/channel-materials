## 3. СЕМЬ СЛОЁВ ОБСЛУЖИВАНИЯ (ядро статьи)

### Слой 1. Диагностика: `hermes doctor`

Единственная команда с гарантированным кодом возврата: `0` - нерешённых проблем нет, `1` - есть хотя бы одна (включая те, что `--fix` не починил). Это позволяет поставить её в health-gate или в CI-шаг.

```bash
hermes doctor          # отчёт
hermes doctor --fix    # попытаться починить автоматически
```

Что проверяет помимо конфига: сетевую связность с API, маршрут IPv6 (короткое 2-секундное соединение; если маршрут объявлен, но уходит в таймаут - предупреждение с подсказкой `network.force_ipv4: true`), структуру конфига. Отдельно ловит классическую граблю: список или словарь, сохранённый как одна строка в кавычках (`plugins.enabled: '["a","b"]'`) - такой список молча игнорируется всеми читателями, плагины не поднимаются. То же предупреждение всплывает в баннере при старте.

Грабля из практики: не запускать `hermes doctor --fix` при живых процессах Hermes. Если doctor не может увидеть процессы - путь починки сам становится вторым писателем в базу.

### Слой 2. База сессий: `hermes sessions`

Один SQLite-файл `state.db` на профиль плюс два сайдкара, которые трогать нельзя. Растёт быстрее, чем наполняется: основной объём даёт не текст переписки, а полнотекстовый индекс поиска.

Подкоманды, которые реально нужны:

| Команда | Что делает | Разрушительность |
|---|---|---|
| `hermes sessions stats` | Статистика хранилища | нет |
| `hermes sessions optimize` | Слияние сегментов FTS5 + VACUUM, данные не трогает | нет |
| `hermes sessions optimize-storage` | Миграция индекса на компактную раскладку v23, на больших базах освобождает заметную долю `state.db` | нет |
| `hermes sessions prune` | Удаление старых сессий, по умолчанию старше 90 дней, куча фильтров | да, но есть `--dry-run` |
| `hermes sessions archive` | Мягкое скрытие теми же фильтрами, требует хотя бы один | обратимо |
| `hermes sessions recover --source <файл> --inspect-only` | Осмотр повреждённой базы без записи | нет |
| `hermes sessions clean-markers` | Вычистка хвостов маркеров вызовов инструментов | нет |
| `hermes sessions pin` / `unpin` / `pinned` | Durable-флаг «не трогать», исключает сессию из автоархива | нет |

**Правило блокировки, о котором надо сказать прямо:** `optimize`, `optimize-storage` и `prune` переписывают хранилище. Если их запустить под живым гейтвеем, все агенты fleet'а начинают отказываться писать в базу с сообщением про «another Hermes process still holds an old copy of the write-ahead log». Поэтому эти команды сначала проверяют, кто держит базу, и отказываются отказываться, печатая список:

```
Refusing `hermes sessions optimize-storage`: another process is using ~/.hermes/state.db.
  PID <1234> (hermes gateway run): state.db, state.db-shm, state.db-wal
  PID <5678> (hermes serve --profile <профиль>): state.db-wal
```

`--dry-run` не блокируется никогда. `--force` обходит - применять только когда знаешь, что процессы простаивают.

Что делать, если такая ошибка уже случилась: остановить все процессы профиля (`hermes gateway stop`, выйти из десктоп-приложения, остановить дашборд через `hermes dashboard --stop`), затем `hermes doctor` покажет, кто ещё держит лог, пока не опустеет список. Ничего не теряется - отказ сделан именно ради этого.

Категорически нельзя: удалять `state.db-wal` или `state.db-shm` (в логе лежат закоммиченные разговоры, которых ещё нет в самой базе - это единственное действие, превращающее отказ в реальную потерю), копировать один `state.db` без сайдкаров, просить агента починить это самому (его собственная сессия лежит в том же хранилище).

### Слой 3. Обучение скиллов: `hermes curator`

Фоновое обслуживание скиллов, созданных агентом. Переводит неиспользуемые скиллы по цепочке `active -> stale -> archived`, плюс раз в цикл поднимает короткую ревизию вспомогательной моделью.

Запуск - не по расписанию, а по простою: срабатывает, если с прошлого раза прошло `interval_hours` (по умолчанию 168 = 7 дней) И агент простаивал `min_idle_hours` (по умолчанию 2 часа). На свежей установке первый реальный проход откладывается на полный интервал - специально, чтобы у тебя было время закрепить важное или выйти.

```bash
hermes curator status              # последний запуск, счётчики, закреплённый список, топ-5 LRU
hermes curator run --dry-run       # показать, что сделал бы, ничего не меняя
hermes curator run                 # запустить сейчас
hermes curator run --consolidate  # форсировать LLM-проход консолидации
hermes curator run --background    # запустить в фоне
hermes curator backup             # ручной снимок ~/.hermes/skills/
hermes curator rollback           # откат с новейшего снимка
hermes curator pause / resume
hermes curator pin <skill>        # никогда не трогать автоматически
```

Две фазы прогона:

1. **Автоматические переходы, без LLM, бесплатно.** Неиспользуемые `stale_after_days` (14) становятся stale, `archive_after_days` (30) уезжают в `~/.hermes/skills/.archive/`. Закреплённые скиллы и те, на которые ссылается любая cron-задача (даже приостановленная), пропускаются целиком. Скиллы с `use_count == 0` получают нижнюю границу: их не архивируют раньше, чем они хотя бы `stale_after_days` старые. Ноль использований - это отсутствие свидетельств, а не доказательство, что скилл не нужен.
2. **LLM-консолидация, выключена по умолчанию.** Сливает пересекающиеся скиллы в зонтики, патчит дрейф. Стоит токенов вспомогательной модели на каждом прогоне и вносит широкие структурные изменения в библиотеку - полная ревизия это 50-100 вызовов API. Включается `curator.consolidate: true` или разово `hermes curator run --consolidate`. Куратор **никогда не удаляет**: худшее, что случится - архивация в `.archive/`, откуда всё возвращается.

Живое состояние хоста: 15 прогонов, последний 4 дня назад. 207 скиллов под управлением куратора (140 активных, 66 stale, 1 в архиве). 346 скиллов вне управления - 142 предшествуют маркеру происхождения, 204 созданы вручную в диалоге. Они не стареют и не архивируются автоматически; передать их куратору - `hermes curator adopt <имя>`. Это отдельная тема для статьи, здесь - факт и команда.

### Слой 4. Чекпоинты и откат: `hermes checkpoints`

Теневой git-хранилище под `/rollback` внутри сессии. У хоста 16.6 МБ, 5 проектов.

```bash
hermes checkpoints                                  # статус: размер, число проектов, разбивка
hermes checkpoints prune --retention-days 3         # чистка
hermes checkpoints prune --max-size-mb 200          # ужать потолок
hermes checkpoints clear-legacy -f                  # вынести архивы v1->v2 миграции
hermes checkpoints clear -f                         # снести всё (необратимо)
```

`prune` игнорирует 24-часовой маркер идемпотентности, чистит осиротевшие и устаревшие проекты, прогоняет GC и соблюдает потолок размера (по умолчанию 500 МБ). Безопасно запускать когда угодно, агент для этого не нужен.

### Слой 5. Бэкап и восстановление: `hermes backup` / `hermes import`

Встроенная команда, и она не то же самое, что сделанный вручную git-бэкап.

```bash
hermes backup                              # полный архив в ~/hermes-backup-<timestamp>.zip
hermes backup -o ~/backups/hermes.zip      # в заданный путь
hermes backup --quick                      # быстрый снимок только критичного состояния
hermes backup --quick --label "pre-upgrade"
hermes backup --keep 5                     # оставить N свежих, 0 = хранить всё
```

Ключевое: использует SQLite API `backup()`, поэтому корректно работает на живом Hermes в режиме WAL. Не вкладывает в архив предыдущие артефакты бэкапа (`backups/`, `state-snapshots/`) - в каждом из них уже своя копия `state.db`.

Коды возврата: `0` только когда каждый выбранный файл попал в архив. Если часть файлов не добавилась - архив сохраняется, но команда выходит `1`, а `--keep` пропускается, чтобы старые полные архивы уцелели. `2` значит, что бэкап уже идёт.

Что исключено из архива: сайдкары `*.db-wal` / `*.db-shm` / `*.db-journal` (в `state.db` уже согласованный снимок, а живой лог рядом дал бы восстановлению полукоммитное состояние), `checkpoints/`, каталоги `models/`, `runtimes/`, `node/` в корне (перекачиваются по требованию, десятки гигабайт), профили браузера с копиями Cookies и Login Data, регенерируемые части `cache/` (каталоги, штампы, spill вывода инструментов; при этом `cache/images`, `cache/audio`, `cache/videos`, `cache/documents`, `cache/screenshots` и `cache/citations` остаются - это доставленные тебе медиа), сокеты и симлинки (zip их не вмещает; до их исключения одинокий `gateway.sock` заставлял каждый полный бэкап рапортовать `Backup incomplete`), и сам код `hermes-agent`. Креды (`.env`, `auth.json`) в полном бэкапе **остаются**.

Восстановление:

```bash
hermes import ~/hermes-backup-20260423.zip
hermes import ~/hermes-backup-20260423.zip --force
```

Перед записью каждый элемент архива распаковывается один раз и проверяется по CRC. Если битый - команда печатает `Error: backup archive is damaged (N member(s) ...)` и выходит `1`, **не тронув Hermes home**. Файлы `.db` не публикуются переименованием: импортированные страницы пишутся внутрь существующего файла базы, чтобы все открытые соединения сошлись на импортированных данных. Если импорт более старого бэкапа поверх более новой работы уменьшает число сообщений - печатается предупреждение с цифрами «было / стало».

Останови гейтвей перед импортом.

Контраст с `hermes profile export`: тот упаковывает один профиль в `.tar.gz` и **вырезает креды** - для переноса и публикации, не для бэкапа.

### Слой 6. Обновления и их безопасность: `hermes update`

Обновление само по себе многослойное: снимок состояния до обновления, обновление кода, валидация синтаксиса девяти критичных файлов с автоматическим откатом через `git reset --hard` при неудаче, подготовка зависимостей, миграция конфига, пересборка десктопа, автоматический рестарт гейтвеев, миграция мультиплекса.

```bash
hermes update --plan     # read-only инвентаризация флота перед обновлением: сервисы, профили, версии, механизм рестарта
hermes update --check    # только сравнение с каналом, без применения
hermes update --backup   # полный zip до обновления
hermes update            # обновиться
```

Режим снимка настраивается отдельно:

```yaml
updates:
  pre_update_backup: full   # quick (по умолчанию) | full | off
  backup_keep: 5
```

У хоста здесь стоит `False`, то есть пред-обновляющих снимков нет вообще. Это сознательный разбор, не жалоба.

Каждый запуск пишет машиночитаемую квитанцию в `~/.hermes/logs/update_receipts/` (хранятся последние 20, `latest.json` всегда указывает на свежую): план флота до обновления, каждый выполненный шаг, что пропущено и почему, исход рестарта гейтвеев и итоговая матрица версий. Если после обновления гейтвей остался на старом коде - команда выходит с ненулевым кодом, чтобы автоматика не считала смешанный fleet здоровым.

Проверка после обновления:

```bash
git status --short      # неожиданно грязное дерево - остановиться и разобраться
hermes doctor
hermes --version
hermes gateway status
hermes pm status
```

Рестарт гейтвея - «сначала сток»: процесс перестаёт принимать новые запросы и ждёт незавершённую работу, с потолком `agent.restart_after_turn_timeout` (30 минут по умолчанию), печатая каждые 30 секунд, что именно он держит. Зависшая работа не удерживает рестарт: сессия, простоя дольше `agent.gateway_timeout`, или прогон крона старше `max(2 * интервал, cron.inflight_max_minutes)` исключаются из ожидания и прерываются.

### Слой 7. Логи, плагины, скиллы, секреты

**Логи** (`hermes logs`): `agent.log` (вся активность), `errors.log` (только предупреждения и ошибки), `gateway.log` (платформы и доставка), `gui.log`, `desktop.log`. Фильтры `--level`, `--since 1h`, `--session <id>`, `--component gateway|cron`, режим `-f`. Ротация через `RotatingFileHandler` - ищите `agent.log.1`, `agent.log.2`. У хоста каталог логов занимает 283 МБ, при `logging.max_size_mb: 5` и `backup_count: 3` - значит, ротация не покрывает часть файлов, и это стоит проверить.

**Плагины** (`hermes plugins`): `list`, `doctor <путь> [--ci]`, `update <имя>`, `enable` / `disable` / `remove`, `install` из каталога. `pack export` выгружает pack-YAML с точными SHA для каждого git-плагина; секреты и разрешения всегда вырезаются. Важно: каталог курируем, кеш 6 часов, каталогизировано не значит проверено - admission смотрит на запись, а не на код.

**Скиллы** (`hermes skills`): `list`, `check` (апдейты хаб-скиллов), `update`, `audit`, `uninstall`, `reset` для залипшего в состоянии `user_modified`, `opt-out` / `opt-in` для управления посевом встроенных скиллов, `snapshot`, `config` для включения по платформам.

**Секреты** (`hermes secrets bitwarden`): `setup`, `status`, `token` (ротация токена с проверкой против Bitwarden до сохранения - отклонённый токен не меняет ничего), `sync --apply`, `install`, `disable`. Суть: ключи берутся из внешнего менеджера при старте процесса, а не лежат в `~/.hermes/.env`.

**Прочее, что стоит упомянуть одной строкой:** `hermes insights` (аналитика токенов, затрат, активности), `hermes usage`, `hermes security`, `hermes prompt-size`, `hermes doctor` в health-gate.

## 4. ТРИ НАХОДКИ, КОТОРЫХ НЕТ В ДОКУМЕНТАЦИИ (сильнее любых общих описаний)

Материал для статьи в первую очередь. Автор настроил систему обслуживания, прогнал её и нашёл в ней три дефекта, которых не видит документация. Ключевое: **все три сформулированы без привязки к машине.** Никаких гигабайт, профилей, PID, путей и имён. Это общие ловушки самодельного обслуживания, а не отчёт о моём диске.

**1. Скрипт бэкапа базы не бэкапится сам.** Еженедельный скрипт зеркалит память, scripts, vault, скиллы, плагины и профили - и всё. Собственный скрипт бэкапа базы лежит в корне git-репозитория бэкапа и ни в один зеркальный каталог не попадает. Проверено: в скрипте синхронизации упоминаний этого файла нет вообще. Скрипт, который каждый день качает базу, хранится только в живом каталоге без страховки. Правило: любой исполняемый файл, который сам ходит по расписанию, обязан лежать внутри зоны, которую обслуживает другой элемент системы.

**2. Мёртвый код в дифф-скрипте.** Функция `export_new_rows` определена, но ни разу не вызвана - логику дублирует инлайновый цикл. Проверено чтением файла. На работу не влияет: цикл работает корректно, водяной знак двигается, данные выгружаются. Классический случай, когда скрипт написан, работает и постепенно обрастает параллельной реализацией того же самого.

**3. Пустой результат, который выглядит как сбой.** Разности выгружаются по водяному знаку: только то, что новее последней отметки. Если между прогонами новых сообщений не было, скрипт честно записал пустые файлы в несколько байт. Из 28 файлов за один день ненулевой ровно один. Проверка показала: в основной базе сообщений много, после водяного знака их единицы - они корректно попадут в следующий дифф. Механика верна, а разброс читается как «сломано», если не знать причину. Урок: у процедуры обслуживания должен быть отчёт, который отличает «нечего сохранять» от «не отработало».

### Выводы, которые читатель не выведет сам

- **Инструменты и окружение перекачиваются.** `tools/` (git, node, python, ffmpeg, chromium), `node/node_modules`, `installs/` - это не данные, а regenerable-окружение. Ровно эти каталоги `hermes backup` исключает как перекачиваемые по требованию. Это правильно, но читатель должен понимать цену: восстановление на новой машине заново качает окружение.
- **Мёртвые копии базы копятся рядом с живой.** Файлы `.bak` и `.bak_cleanup` от прошлых обновлений лежат месяцами. Документация советует хранить снимки аварийного обновления «пока не поработаешь с обновлённым приложением». Никто не хранит их «недолго». Готовая статья в диске, которую никто не читает.
- **Снимки перед обновлением и резервная копия - разные вещи.** При выключенном `updates.pre_update_backup` новых снимков не будет, и единственный путь отката - собственный скрипт, который сам ничем не защищён.
- **Штатные процедуры обслуживания не запускаются просто потому, что про них не вспомнили.** Ни разу выполненные `sessions optimize` / `optimize-storage` при базе, которую имеет смысл оптимизировать, - самая дешёвая выгода из всех.
- **`sessions.auto_prune` выключен при включённом `auto_archive`.** Мягкое скрытие работает, необратимого ухода старых сессий нет - база растёт только вверх.
- **Скиллы, созданные агентом вручную в диалоге и появившиеся до маркера происхождения, куратор не видит.** Они не стареют и не архивируются, пока не будет `hermes curator adopt`. В библиотеке их заметная доля.
- **Встроенный `hermes backup` по расписанию может не запускаться вообще.** Тогда пути восстановления через `hermes import` нет, и согласованный снимок базы делает отдельный скрипт.

## 5. ТРЕБОВАНИЯ К СТРУКТУРЕ

Тон B, авторитетный, попроще: короткие предложения, тезис - доказательство - следующий тезис. Без корпоративного жаргона («синергия», «экосистема», «компетенции»). Без «я облажался» - автор на три шага впереди, он не чинит, он описывает процедуру.

Порядок сборки:

1. Заход: бэкап настроили, вопрос закрыт, а агент всё равно раздувается. Назвать цену конкретно: база растёт, рядом копятся мёртвые копии, кэш и перекачиваемое окружение занимают место, а диск заполняется. Показать это как следствие, а не как опись машины автора.иска.
2. Карта: семь слоёв одним списком с командами. Читатель должен за один взгляд понять, чего у него нет.
3. Каждый слой - одинаковый шаблон: **что это / как запустить / когда нужно / когда НЕ нужно / что ломается**. Одинаковый шаблон - читатель находит своё за секунды. Грабли сразу после слоя, а не одной секцией в конце.
4. Живые цифры хоста как сквозной пример, а не как «у меня тут».
5. Блок «Чек-лист первой настройки» - команды в порядке запуска, с пометкой, что необратимое (`prune`, `clear`, `doctor --fix` под живыми процессами) требует остановки.
6. Блок «Когда это НЕ нужно» - честный. У однопользовательского агента на ноутбуке половина слоёв закрыта по умолчанию. Признать.
7. Блок «Чем встроенное отличается от самодельного» - сравнение `hermes backup` с git-бэкапом в приватный репозиторий: зоны покрытия не пересекаются полностью, одно не заменяет другое. Это честный вывод, а не продажа.

Обязательные блоки: **Premortem** (для аналитики), **Cost** (всё бесплатно, но диск и время пересчитать), **Alternatives** (чем не заменить), **Code/Reproducibility** (ссылка на документацию).
