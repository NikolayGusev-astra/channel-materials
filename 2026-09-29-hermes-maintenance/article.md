# Как обслуживать агента: семь слоёв, о которых не думают

Сегодня умер блок питания. Без предупреждения, без аварийного режима, без "успел сохранить". Сама поломка - событие на пять минут, случается раз в пять лет. А вот то, что после неё приходится собирать заново часами, - не авария, а часть ежедневной работы, которую по умолчанию никто не делает.

Мы упускаем ровно то, что кажется очевидным. Мы уверены, что агента настроили, потому что помним, как настраивали. Мы считаем, что бэкап настроен, потому что бэкап когда-то сработал. Самое очевидное и есть то, мимо чего проходят.

Ниже - порядок обслуживания. Не про то, что делать, когда всё уже сломалось, а про то, чтобы до этого не доводить.

## Три части, на которые всё делится

Каталог агента делится на три сорта. С деления полезно начинать: от него зависит, что бэкапить, а что - нет.

**Часть первая. Настройки, ключи, скиллы, тулы.** Маленький объём, высокая ценность: конфигурация, доступы, скиллы, плагины, память. Восстанавливается минутами, если оно есть, и никак, если нет.

**Часть вторая. История сессий в базе.** Переписка, состояние диалогов, полнотекстовый индекс. Самая тяжёлая по объёму и самая хрупкая: индекс раздувается, и база растёт быстрее, чем наполняется.

**Часть третья. Перекачиваемые пакеты.** Python, Node, ffmpeg, Chromium, Git, зависимости, кэш. Единственная часть, где правильный ответ "не копировать".

Смешать первую со второй - потерять переписку. Смешать вторую с третьей - тащить по сети то, что перекачается при первом же запуске.

Дальше - по каждому слою: что с ним делать и что случится, если не делать ничего.

## Семь слоёв

Каждый слой относится к одной из трёх частей.

### 1. Диагностика: `hermes doctor`

*Часть 1: настройки, ключи, скиллы, тулы*

Единственная команда с честным кодом возврата: 0 - нерешённых проблем нет, 1 - есть хоть одна, включая непочиненные. Годится как гейт перед релизом.

```bash
hermes doctor          # отчёт
hermes doctor --fix    # попытаться починить
```

Проверяет и связность с API: если система объявляет IPv6, но соединение уходит в таймаут, предложит `network.force_ipv4: true`.

Ловит классическую граблю: список, сохранённый как одна строка в кавычках, например `plugins.enabled: '["a","b"]'`. Все читатели его молча игнорируют, плагины не поднимаются, объяснения нет.

**Грабля:** не запускать `doctor --fix` при живых процессах - путь починки сам станет вторым писателем в базу. Хуже, чем ничего не чинить.

### 2. База сессий: `hermes sessions`

*Часть 2: история сессий*

SQLite-файл `state.db` на профиль плюс два сайдкара, которые нельзя трогать. Растёт быстрее, чем наполняется: основной объём даёт не текст переписки, а полнотекстовый индекс.

```
hermes sessions stats
hermes sessions optimize           # слияние сегментов FTS5 + VACUUM
hermes sessions optimize-storage   # компактная раскладка индекса, экономит много
hermes sessions prune             # удалить старое, по умолчанию старше 90 дней
hermes sessions archive           # мягко скрыть, обратимо
hermes sessions pin <id>          # не трогать автоматически
hermes sessions recover --source <файл> --inspect-only
```

`optimize` не трогает данные. `optimize-storage` заметно уменьшает файл, потому что перекладывает индекс. У `prune` есть `--dry-run`, перед удалением лучше сделать `export`.

**Главное правило слоя.** `optimize`, `optimize-storage` и `prune` переписывают хранилище, а под живым гейтвеем весь парк агентов начнёт отказываться писать в базу. Поэтому эти команды сначала смотрят, кто держит файл, и отказываются:

```
Refusing `hermes sessions optimize-storage`: another process is using <каталог агента>/state.db.
  PID <1234> (hermes gateway run): state.db, state.db-shm, state.db-wal
  PID <5678> (hermes serve --profile <профиль>): state.db-wal
Stop them first, then re-run. Override with --force if you accept the risk.
```

`--dry-run` не блокируется никогда. `--force` обходит проверку, применять только когда точно знаешь, что процессы простаивают.

Если отказ случился: остановить всё (`hermes gateway stop`, выйти из приложения, `hermes dashboard --stop`), затем `hermes doctor` покажет, кто ещё держит журнал, и повторять, пока список не опустеет. Данные при этом не теряются.

Категорически нельзя: удалять `state.db-wal` или `state.db-shm` - там закоммиченные разговоры, которых ещё нет в базе, и это единственное действие, превращающее отказ в реальную потерю. Также нельзя копировать `state.db` без сайдкаров и просить агента починить это самому.

### 3. Скиллы: `hermes curator`

*Часть 1: настройки, ключи, скиллы, тулы*

Переводит неиспользуемые скиллы по цепочке `active` → `stale` → `archived`.

```bash
hermes curator status
hermes curator run --dry-run    # посмотреть, не меняя
hermes curator run
hermes curator backup           # снимок skills/
hermes curator rollback
hermes curator pin <skill>
```

Запуск не по расписанию, а по простою: `interval_hours` (168, неделя) плюс `min_idle_hours` (2 часа). На свежей установке первый проход откладывается на полный интервал.

Первая фаза - автоматические переходы, бесплатно: 14 дней без использований → `stale`, ещё через 30 → `.archive/`. Закреплённые скиллы и те, на которые ссылается cron-задача, пропускаются. Скиллы с нулём использований не архивируют раньше тех же 14 дней: ноль использований - отсутствие свидетельств, а не доказательство ненужности.

Вторая фаза - консолидация моделью, выключена по умолчанию: сливает пересекающиеся скиллы в зонтики, 50-100 запросов к API. Куратор **никогда не удаляет**, только архивирует.

Грабли: скиллы, созданные агентом вручную в диалоге, и скиллы, появившиеся до маркера происхождения, куратор не видит. Они не стареют и не архивируются, пока не будет `hermes curator adopt`.

### 4. Чекпоинты: `hermes checkpoints`

*Часть 1, но весит отдельно*

Теневое git-хранилище за `/rollback` внутри сессии.

```bash
hermes checkpoints                        # статус
hermes checkpoints prune --retention-days 3
hermes checkpoints prune --max-size-mb 200
```

`prune` чистит осиротевшие и устаревшие проекты, прогоняет сборку мусора и соблюдает потолок размера (500 мегабайт по умолчанию). Безопасно запускать когда угодно.

### 5. Бэкап: `hermes backup`

*Части 1 и 2. Часть 3 в архив не попадает сознательно*

```bash
hermes backup                              # ~/hermes-backup-<метка>.zip
hermes backup --quick --label "pre-upgrade"
hermes backup --keep 5
```

Работает на живом Hermes: использует API `backup()` из SQLite, журналирование значения не имеет.

Код возврата говорящий. `0` - попал каждый файл. Если что-то не добавилось, архив сохраняется, но команда выходит `1`, а `--keep` пропускается, чтобы старые полные архивы уцелели. `2` - бэкап уже идёт. Крон не сообщит об успехе при неполном архиве.

Исключено: сайдкары `*.db-wal` и `*.db-shm`, `checkpoints/`, `models/`, `runtimes/`, `node/`, профили браузера с Cookies и Login Data, регенерируемые части `cache/`. Остаются `cache/images`, `cache/audio`, `cache/videos`, `cache/documents`, `cache/screenshots` - доставленные тебе медиа. Ключи и `auth.json` тоже остаются: это миграция, а не публикация.

Восстановление - `hermes import <файл>`. Перед записью каждый элемент проверяется по контрольной сумме; битый - команда выходит `1`, не тронув каталог ни байтом. Базы публикуются не переименованием, а записью страниц внутрь существующего файла, и старый бэкап поверх новой работы печатает предупреждение, если сообщений стало меньше. Перед импортом остановить гейтвей. Отличие от `hermes profile export`: тот упаковывает один профиль в `.tar.gz` и **вырезает ключи** - это для переноса, а не для бэкапа.

### 6. Обновления: `hermes update`

*Часть 3: перекачиваемые пакеты*

Обновление многослойное: снимок состояния, код, проверка синтаксиса девяти критичных файлов с автооткатом, зависимости, миграция конфигурации, перезапуск.

```bash
hermes update --plan   # инвентаризация парка, только чтение
hermes update --check  # сравнить с каналом
hermes update --backup # полный архив перед обновлением
hermes update
```

```yaml
updates:
  pre_update_backup: full # quick (по умолчанию) | full | off
```

Каждый прогон пишет квитанцию в `logs/update_receipts/`: что было до обновления, каждый шаг, что пропущено, итоговая таблица версий. Если гейтвей остался на старом коде, команда выходит с ненулевым кодом - автоматика не примет разнородный парк за здоровый.

Перезапуск идёт "сначала сток": ждёт незавершённую работу с потолком 30 минут, печатая каждые 30 секунд, что именно держит.

Проверка после обновления: `git status --short`, `hermes doctor`, `hermes --version`, `hermes gateway status`, `hermes pm status`.

### 7. Логи, плагины, скиллы, ключи

*Часть 1: настройки, ключи, скиллы, тулы*

`hermes logs` показывает `agent.log`, `errors.log` (только ошибки), `gateway.log`, `gui.log`, `desktop.log`. Фильтры `--level`, `--since 1h`, `--session <id>`, `--component gateway`. Грабли: ротация вида "5 мегабайт, хранить 3" не покрывает часть файлов - каталог логов растёт, пока не проверишь его `du`.

`hermes plugins doctor <путь> --ci` проверяет через настоящий загрузчик: каталог курируем, но каталогизировано не значит проверено.

`hermes skills check`, `update`, `audit`, `reset`, `opt-out` - обновления, аудит и сброс залипших скиллов.

`hermes secrets bitwarden token` - ключи берутся из внешнего хранилища при старте процесса, а не лежат в файле окружения. Ротация сначала проверяет новый токен: отклонённый не меняет ничего.

Плюс `hermes insights` (аналитика токенов и затрат), `hermes usage`, `hermes security`.

## Что делать в первую очередь

Порядок для начинающих.

```
1. hermes sessions stats           осмотреться
2. hermes curator status           что с скиллами
3. hermes checkpoints              сколько занимает откат
4. hermes doctor                   базовая диагностика
5. hermes backup --quick --label first
6. hermes sessions optimize        освободить место, данные не страдают
7. разобрать .bak рядом с базой     половина - мусор
8. hermes curator adopt <имя>      передать скиллы куратору
```

Шаги 6 и 7 требуют остановки гейтвея либо `--force`. Шаг 7 - удаление файлов, но сначала убедись, что свежий бэкап есть.

## Три грабли, на которые наступают

Ловушки без сообщения об ошибке: всё выглядит исправным, ломается позже.

**Скрипт обслуживания, который никто не обслуживает.** Файл, который ходит по расписанию, лежит вне зоны, которую зеркалит бэкап. Еженедельный скрипт копирует память, скиллы, плагины и профили, а собственный скрипт бэкапа базы лежит в корне репозитория и не попадает ни в одну из этих зон. Правило простое: всё, что попадает в архив, должно лежать в каталогах, которые архив покрывает.

**Две реализации одной функции в одном скрипте.** Функция, которая делала ровно то, что нужно, - и инлайновый цикл рядом, который делал то же самое. Функция не вызывалась ни разу, данные выгружались правильно, проверки проходили. Любой работающий скрипт со временем обрастает параллельной копией себя, и найти её можно только перечитыванием.

**Пустой результат, неотличимый от сбоя.** Разности выгружаются по водяному знаку: только то, что новее последней отметки. Если между прогонами новых сообщений не было, скрипт записал пустые файлы в несколько байт. Механика верна, а выглядит как "всё сломалось". У процедуры должен быть отчёт, отличающий "нечего сохранять" от "не отработало".

## С чего начать

Часть слоёв можно не делать. Если переезжать некуда и конфигурация лежит в git, встроенный `hermes backup` избыточен. Если `/rollback` ни разу не пригодился, чекпоинты не нужны. Если база маленькая, `optimize-storage` не окупит остановки гейтвея. Если библиотека скиллов небольшая, консолидация куратора не окупится. Диагностика, `optimize` и разбор мёртвых копий нужны всем, у кого агент живёт дольше пары месяцев.

Всего - 30 команд и около 20 минут работы, из которых основное время уходит на ожидание: `optimize-storage` на большой базе считает минуты, `hermes update` перезапускает гейтвеи, `hermes doctor --fix` перечитывает конфиг. Одной команды нет: `hermes backup` не чистит скиллы, `hermes curator` не трогает базу, `hermes sessions optimize` не выгружает кэш. И слои не независимы: `hermes update --backup` зовёт слой "бэкап", `hermes doctor` показывает, кто держит базу в слое "сессии", куратор пропускает скиллы, на которые ссылается cron. Каждый слой обслуживает себя и подстраховывает соседний.

Обслуживание - не набор хитрых команд, а семь слоёв, каждый либо настроен, либо нет. Бэкап закрывает один. Остальные шесть молча копятся, пока не съедят диск, не потеряют откат или не превратят библиотеку скиллов в свалку.

Порядок действий: пройти пункты с 1 по 8 из чек-листа выше, разобрать содержимое каталога с базой по дате, снять первый полный `hermes backup` и положить его на диск, который не является системным. Дальше - по одному слою в неделю.
