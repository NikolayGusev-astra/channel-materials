# Агенты в DevOps: три слоя и почему CLI выигрывает

Агент в DevOps отличается от агента-редактора кода одной вещью: он ходит в системы, которые
никто не откатит кнопкой. Код можно посмотреть в diff перед мержем. Прод на стенде нет. Отсюда
растёт всё остальное, в том числе то, как устроен его инструментарий.

## Три слоя

```
слой 1. ЗНАНИЕ     скиллы: что делать, в каком порядке, какие грабли
слой 2. ИСПОЛНЕНИЕ  CLI и скрипты: как именно выполнить
слой 3. ДОСТУП     MCP-серверы: куда идти за состоянием
```

Ни один слой не заменяет другой. Скилл без CLI остаётся советом, CLI без скилла работает вслепую,
MCP без первых двух - дорогой способ узнать то, что терминал отдаёт бесплатно.

Слой 1. Скилл - текстовый файл `SKILL.md` с инструкцией, которую агент читает по триггеру. В
frontmatter есть `name` и `description`, и `description` важнее: он триггер, и если там нет слов,
которыми задача будет сформулирована, скилл просто не сработает. `name` и имя каталога - разные
вещи, совпадать они не обязаны. Ломает работу только коллизия, когда два скилла носят одно `name`:
агент получает два конкурирующих определения, и выбор между ними не виден ни тебе, ни ему.

Слой 2. CLI - то, через что исполняется всё. Скилл про Docker не запускает Docker: он объясняет
порядок действий, а исполняет его `docker`.

Слой 3. MCP нужен там, где у CLI нет: Jira, Confluence, Mattermost, внутренние каталоги
уязвимостей. Это ровно те системы, у которых нет нормального терминального клиента.

## Как слои стыкуются

Схема одна на все домены, разница только в том, куда скрипт ходит за состоянием.

```
постановка задачи
   ↓
диспетчер выбирает скилл                    слой 1: знание
   ↓
скрипт вызывает CLI с параметром            слой 2: исполнение
   ↓
получает JSON, разбирает, сверяет
   ↓
при необходимости идёт в MCP за статусом   слой 3: доступ
   ↓
вывод: значение или отчёт
```

Пример на стоящей задаче, проверка состояния сервиса на стенде:

```
скрипт (paramiko, слой 2)
   → ssh на стенд
      → sudo -n systemctl is-active YOUR_SERVICE.service
      → sudo -n psql -d YOUR_DB -tAc "SELECT ..."
   ↓
вывод в JSON: сервис активен, очередь N, текущее значение счётчика
   ↓
сверка с ожиданием в скилле (слой 1)
   ↓
если расходится - алерт и запись в отчёт
```

Тот же паттерн работает для VPN, для сайтов и для репозиториев. Меняется только первый шаг:
чтение конфига вместо вызова CLI, или `git log` вместо `systemctl`.

Два требования к скрипту в этой схеме. Первый: нумерация шагов и идентификатор в начале каждой
строки вывода, иначе диагностика не отличит «не дошли» от «дошли и упали». Второй: скрипт
обязан явно отличать «проверка выполнена и пусто» от «до системы не дошли», иначе пустой вывод
считается успехом.

## Что показывают замеры

### Масштаб внедрения: 90 процентов, но не в тех слоях

Опрос JetBrains Developer Ecosystem 2026, больше 15 000 разработчиков, май-июль 2026:

| Показатель | Значение |
|---|---:|
| Используют агентов на работе хотя бы раз в неделю | 90% |
| Используют ежедневно | 68% |
| Claude Code на работе | 39% (в январе 2026 было 18%) |
| Codex | 16% (в январе 3%, рост примерно в 5 раз) |
| GitHub Copilot | 21% (год назад 29%) |
| Cursor | 12% (в январе 18%) |
| OpenCode | 7% при известности 42% |
| Известность GitHub Copilot | 79% |

Известность и использование разошлись. Copilot по-прежнему знают почти все, 79 процентов, но
используют 21 процент. Claude Code обошёл его вдвое за полгода. OpenCode при 7 процентах
использования имеет 42 процента известности: за ним не стоит крупная компания, но о нём знает
вдвое больше людей, чем им пользуется.

Отсюда порядок выбора: смотреть не на текущую долю, а на скорость её изменения. Инструмент
всплывает раньше, чем успевает обзавестись документацией, и выбирающий по установившейся доле
систематически опаздывает на один виток.

### Где болит: 64 процента против 32

DevOps Conf 2026, метаанализ более 50 исследований:

| Показатель | Значение |
|---|---:|
| Используют генерацию часто или всегда | 58% |
| Видят рост личной продуктивности | 64% |
| Видят рост командной продуктивности | 32% |
| Качество кода: лучше / хуже | 32% / 14% |
| Не доверяют AI-коду | 49% |
| Редко используют: code review | 24% |
| Редко используют: legacy | 18% |

Разрыв 64 против 32 - главная цифра отчёта. Личная выгода есть у двух третей инженеров,
командная у трети, и объяснение не в том, что агент не работает. Он ускоряет то, до чего раньше
руки не доходили. Если узкое место было в ревью, код приходит быстрее, чем человек его
проверяет, и эффект обнуляется на ревью.

Отсюда правило для архитектуры агента: автономию ограничивают там, где узкое место, а не там,
где монотонно. Ограничение на создание pull request бессмысленно, если ревью и тесты и так
узкое место. Ограничивать надо выкладку, а не набор текста.

DORA 2025 формулирует то же на своём языке: AI усиливает уже существующие сильные и слабые
стороны организации. Отдача приходит не от инструментов, а от того, что сделано с процессом
вокруг них.

### Экономика CLI против MCP: 275 раз на задачу

GitHub MCP Server: 93 инструмента, около 55 000 токенов только на схемы, до того как прочитан
хоть один файл. С Jira и базой - 150 000 токенов, что больше окна некоторых моделей. Та же
задача через `gh` - около 200 токенов. Разница в 275 раз.

Playwright: сервер отдаёт полное дерево доступности страницы, на сложной странице это тысячи
узлов и 12 000 символов за один клик, плюс 26 определений инструментов, около 3 600 токенов до
начала работы. Бенчмарки команды Playwright дают разницу в 4 раза по потреблению и до 10 раз
в длинных сессиях: с MCP в контексте копятся все предыдущие снимки страниц. В отчёте Better
Stack CLI потратил 16 процентов окна на многошаговую задачу, MCP 18 процентов, причём с MCP
задача не была выполнена вовсе, шаг со скриншотом провалился.

Vercel agent-browser: 17 инструментов свёрнуты до 2, ускорение в 3,5 раза, токенов на 37
процентов меньше, success rate с 80 до 100 процентов, при том же бюджете контекста
выполняется в 5,7 раза больше тестовых циклов.

Scalekit, 75 прогонов, Claude Sonnet 4: CLI 25 из 25 успешно, MCP 18 из 25, семь запросов
провалились по таймауту. По деньгам при десяти тысячах операций в месяц: 3,20 доллара против
55,20.

MCP дорог не деньгами, а ненадёжностью. Семь провалов по таймауту из 25 не лечатся ни увеличением
бюджета, ни улучшением промпта: таймаут удалённого сервера не зависит от того, насколько хорошо
агент сформулировал запрос.

MCP всё-таки нужен там, где CLI бессилен: многопользовательские системы с OAuth 2.1,
per-session RBAC и аудитом; сервисы без CLI; среды без терминала; корпоративная среда, где
неограниченный shell к агенту сам по себе инцидент. Формулировка точная: каждое преимущество
CLI при автоматизации чужого workflow становится архитектурной уязвимостью.

### Skills как третий путь

Skill оборачивает любой транспорт в один интерфейс: с ~55 000 токенов схем Jira MCP до ~300
токенов на конкретное действие, причём агент не знает, что под капотом, и не должен знать.
Бизнес-контекст добавляется, стоимость подключения не растёт.

Отсюда деление скиллов на типы. Вендорский прячет за интерфейсом исполнение через CLI. Локальный
прячет то, чего нет ни в одной документации: где лежат артефакты, что исключать из аудита, в
каком порядке запускать сканеры. Транспорт подменяется под слоем и не протекает в контекст.

Anthropic движется в ту же сторону: в Claude Code появился экспериментальный режим, где
MCP-инструменты грузятся через CLI-обёртку, а не в контекст напрямую, с экономией до 80
процентов занятого контекста.

### Экосистема MCP жива

PulseMCP индексирует больше 12 000 серверов уже после фильтрации низкокачественных
реализаций, протокол с конца 2025 года курирует Linux Foundation. Мёртвой технологии такое не
случается, и 275-кратная разница в токенах не делает MCP пережитём в любом окружении.

Правило входа: начинать с read-only и выдавать права записи только когда поведение агента
проверено. У GitHub MCP есть флаг `--read-only`, запрещающий любые изменения целиком. Отдельный
сервисный аккаунт с минимальными правами вместо своего. К production-базам доступа на запись
нет. Три строки, и они дешевле любого инцидента.

Границы применимости, о которых стоит знать до подключения. Kubernetes MCP требует, чтобы
кластер уже был в kubeconfig, с облачными провайдерами из коробки не работает. Grafana MCP
оптимизировал структуру ответов ради экономии контекста, то есть токеновая проблема решается
на стороне сервера, если сервер этого хочет. Prometheus MCP переводит естественный язык в
PromQL - случай, где MCP даёт то, чего CLI не даст: готовый запрос, который вы бы не написали
руками.

## Итог

Три слоя, и ни один не заменяет другой. Ошибка новичка - выбрать один слой и упереться. Ошибка
опытного - не заметить, что агент траит контекст на схемы, которые ему никогда не понадобятся.

Наличие сотен скиллов в папке и двадцати подключённых MCP-серверов не значит, что агент всё это
знает. Значит, что у него есть выбор. Скилл, который не загружен, в контекст не попадает, и агент
не может по нему ошибиться. Поэтому диспетчер важнее количества скиллов, а `--read-only`
важнее количества подключённых серверов.

именно они отвечают на вопрос, на который документация не отвечает никогда: не «как устроен
инструмент», а «что делать здесь, с нашими ограничениями».

Пять официальных наборов не заменяют ни Gitleaks, ни Trivy, ни Semgrep, ни Bandit, ни
ShellCheck, ни mypy, ни pip-audit. Это разные задачи: Cloudflare из 14 скиллов даёт разработку
и hardening на платформе, а не поиск дыр в чужом коде.

Отбор сводится к двум вопросам. Первый: скилл про использование инструмента или про его
разработку? Про разработку не берём, пока нет такой задачи. Второй, важнее: скилл молча
предполагает, что у вас Linux и свежий дистрибутив? Официальный скилл не знает про ваши стенды
и ваши договорённости.

Порядок загрузки вендор задаёт сам, и он не произвольный. Для Docker это `project-foundations`
перед `build-strategies`, `destructive-guardrails` перед любым `rm` и `prune`. Нельзя запускать
агента до того, как написан конфиг, и нельзя трогать volumes до того, как прочитан скилл о
последствиях.

Аудит своего набора начинается с неприятного открытия: сначала выясняется, что скиллов
неизвестно сколько. Обход `glob(SKILLS, "*", "*")` смотрит ровно два уровня вложенности и
на этой установке находит 371 скилл при 541 реальном, то есть 160 выпали из выборки, а вердикт
«битых ссылок ноль» оказывается верным случайно. Дальше видно, что часть пропавших файлов
лежит в `.archive/`: скиллы объединяли при дедупликации, файлы уезжали в архив, а `SKILL.md`
продолжал на них ссылаться.

Самое неприятное открытие аудита: битая ссылка на несуществующий reference не вызывает
ошибки. Агент прочитает её, не найдёт файла и пойдёт дальше, строя план по содержанию, которого
не видел. Скрипт, зовущий несуществующий бинарь, хотя бы вернёт ошибку. Поэтому аудит ссылок
полезнее чистки каталогов.
