# Model routing для агентных задач: как перестать тратить сильную модель на переименование переменной

*Хаб: «Искусственный интеллект». Теги: ai-agents, llm, open source, сезон Код будущего.*

У меня несколько подписок на модели и несколько бесплатных API. В какой-то момент я заметил неприятную закономерность: лимит сильной модели заканчивался не на архитектуре и не на сложном отладочном сеансе. Его съедали десятки мелких поручений: найти строку, объяснить ошибку линтера, переименовать поле.

Это не проблема дисциплины пользователя. Агент по умолчанию не знает цену следующего запроса и не умеет различать «простую работу» и «работу, где ошибка дорого стоит». Я решил относиться к выбору модели как к маршрутизации в сети: сначала классифицировать пакет, потом отправлять его по подходящему маршруту, а при отказе менять не только модель, но и провайдера.

## Почему переключение между моделями одного сервиса не является резервированием

У провайдера обычно общий лимит аккаунта, а не независимый лимит каждой модели. Поэтому цепочка `сильная → средняя → быстрая`, если все три принадлежат одному поставщику, создаёт иллюзию отказоустойчивости. При исчерпании общего лимита она тратит время на две заведомо неудачные попытки.

У бесплатных API другая картина: лимит запросов в минуту, дневной порог, временная недоступность конкретной модели. Значит, роутер должен хранить состояние не только модели, но и провайдера: причина отказа, время следующей попытки, доступные возможности и стоимость.

## Классификация до вызова

Для первого варианта я не стал вызывать LLM, чтобы другая LLM выбрала LLM. Это добавило бы цену, задержку и непрозрачность. Вместо этого используется детерминированный счётчик сигналов.

| Сигнал в задаче | Балл |
|---|---:|
| Несколько подзадач, полный поиск по репозиторию | +4 |
| Архитектура, миграция схемы, широкий эффект | +3 |
| Безопасность, необратимое действие, отладка | +2 |
| Правки в нескольких файлах, распараллеливание | +2 |
| Длинный запрос или известный сложный навык | +1–2 |
| Переименование, форматирование, одна строка | −2 |

Сумма 0–2 означает `quick`, 3–5 — `standard`, 6–9 — `deep`, от 10 — `architect`. Границы не претендуют на универсальность: важнее, что они видны человеку. Если задача ушла в дорогой класс, в логе можно прочитать, какие признаки это вызвали.

```python
def classify(task: str, files: int) -> str:
    score = 0
    score += 4 if any(x in task.lower() for x in ("все использования", "разбей", "план")) else 0
    score += 3 if any(x in task.lower() for x in ("архитектура", "миграция", "схема")) else 0
    score += 2 if files >= 3 or "безопас" in task.lower() else 0
    score -= 2 if "переимен" in task.lower() and files == 1 else 0
    return "quick" if score <= 2 else "standard" if score <= 5 else "deep" if score <= 9 else "architect"
```

Это не оценка интеллекта задачи. Это оценка риска ошибиться, цены ожидания и ожидаемой пользы от сильной модели.

## Маршруты и причины переключения

У каждого класса — короткая цепочка. Например, рутинный запрос начинается с недорогой модели, затем переходит к независимому бесплатному провайдеру, и только после этого — к модели из основной подписки. Глубокая диагностика, наоборот, начинает с сильной модели, но запасной путь обязательно ведёт к другому поставщику.

Ключевое правило: один и тот же провайдер не должен занимать соседние позиции в маршруте. Исключение — явное поручение человека: если он попросил конкретную модель, автоматике не следует спорить.

Не менее важен разбор ошибки. `usage limit` означает отключить весь аккаунт поставщика. HTTP 429 — перейти к следующему звену и назначить повтор после окна лимита. Сетевая ошибка не равна лимиту: её надо пометить отдельно, иначе роутер выведет из строя здоровый канал.

```json
{"class":"deep","provider":"primary","model":"terra","result":"fallback","reason":"account_limit"}
```

Такой JSONL-журнал — не украшение. Через неделю он отвечает на вопросы, которые иначе обсуждают по ощущениям: сколько задач дошло до дорогой модели, какие отказы повторяются и не слишком ли строгий порог у класса `deep`.

## Цена «бесплатной» модели

Бесплатный доступ не делает модели взаимозаменяемыми. В независимом Terminal-Bench одна из доступных моделей могла решать около 47,6% задач, а другая с громким именем — около 19,1%. Нулевая цена второго варианта не компенсирует повторный запуск, ручную проверку и повреждённый контекст агента.

Я выбираю кандидат сначала по необходимой способности: инструменты, размер контекста, мультимодальность, качество кода. Затем сверяю сравнимые бенчмарки, выполненные одним харнессом. И только затем смотрю на цену. Заявления производителей полезны как подсказка, но цифры из разных наборов сравнивать нельзя.

## Что изменилось после недели логов

Около 70% рутинных задач стали заканчиваться на первом дешёвом или бесплатном звене. Сильная модель осталась для проектирования, сложной отладки и ревью безопасности. Лимит основной подписки перестал быть аварией: после его исчерпания агент не делает три бессмысленных запроса в тот же сервис, а продолжает работу по независимой ветке.

Маршрутизатор не делает слабую модель сильной. Он делает расход и деградацию предсказуемыми. Для этого достаточно описать свой инвентарь, выписать несколько наблюдаемых сигналов сложности, задать разные причины отказа и не забыть собирать журнал.
