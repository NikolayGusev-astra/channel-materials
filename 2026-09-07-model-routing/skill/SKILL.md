# model-routing — выбор модели по способностям под задачу

Принцип: модель выбирается по тому, ЧТО она умеет (бенчи, контекст,
модальности, tools), а не по факту бесплатности. Бесплатная модель с 1%
terminal-bench хуже платной с 70%. Цена — второй фильтр после пригодности.

### 1.1. Локальный endpoint — отдельный класс провайдера

LM Studio / Ollama / любой OpenAI-compatible локальный сервер (`OPENAI_BASE_URL`
указывает на `http://127.0.0.1:<port>/v1`) — это **прямой вызов без сети**,
через мой OpenAI-интерфейс. Принципиально отличается от облачных провайдеров:

- **Лимитов нет.** Нет 429, нет дневного капа. Ограничение — только железо (VRAM,
  RAM, диск) и качество самой модели. Если LM Studio отдаёт ответ — это потому
  что выбранная модель его родила, а не потому что провайдер отрезал.
- **Каталог живой, но чужой.** Список моделей — `curl $OPENAI_BASE_URL/v1/models`.
  Это **список чек-поинтов на диске юзера**, а не облачный каталог. Имена могут
  быть произвольные (`liquidai_lfm2.5-2.6b`, `qwen2.5-coder-7b-instruct-q4`,
  и т.п.), это не `provider/model` формат OpenRouter.
- **Бенчей нет в OpenRouter-style.** Kilo / OpenRouter не меряют локальные
  модели. Качество известно только юзеру или из community-источников
  (HuggingFace model card, LM Studio leaderboards). Роутер не может сам
  оценить пригодность — если юзер не указал явно, локальную модель для
  содержательных задач НЕ берём.
- **Прокси vs localhost.** `http_proxy` (установлен глобально на этом хосте)
  пытается залезть на `127.0.0.1:1234` и получает 502. Перед вызовом
  локальной модели — `NO_PROXY=127.0.0.1,localhost` ИЛИ передавать `proxies=`
  явно, иначе первый же запрос к LM Studio провалится.

**Когда роутер использует локальную модель:**
- Только если в `~/.hermes/config.yaml → model.default` или в активном профиле
  **юзер явно** поставил локальный endpoint. Это НЕ скилловое решение — это
  конфиг-факт, который роутер уважает.
- Роутер НЕ предлагает «давайте прокачаем локальный чек-поинт» как
  альтернативу облачному free — у роутера нет данных о качестве локальной
  модели. Если юзер хочет роутить на локальные — отдельная настройка.

**Если оркестратор (= ассистент) запущен на локальной модели** (`model.default` =
локальный endpoint в конфиге), и эта модель **меньше 7B** — скилл `model-routing`
**деградирует**: скоринг-таблица и правила переключения требуют, чтобы оркестратор
понимал, что он делает. Модели <7B (lfm2.5-2.6b, gemma-2-2b) будут ошибаться в
применении правил. Минимум для оркестратора с model-routing — 7B
(qwen2.5-coder-7b, mistral-nemo, gemma-2-9b). Иначе выбирай модель сама, без
скилла.

### 1.1.1. Валидированный локальный оркестратор: google/gemma-4-e4b

**Тестировано 2026-09-07, LM Studio 127.0.0.1:1234.** Модель Gemma 4
effective 4B (MoE-эксперты, активны ~4B) — **реально работает как диспетчер**.

**Что умеет:**
- ✅ Следует инструкции «вызови bash, не решай сам» — выдаёт точную
  команду `hermes-route "task"` (на английском system — безупречно,
  на русском — тоже, но тратит больше reasoning_tokens)
- ✅ Делает скоринг по сигналам и выбирает категорию (на тесте
  "найди все deprecated API и почини" дала SCORE 14, CATEGORY architect —
  лучше чем детерминированный route.py, который дал SCORE 4)
- ✅ Понимает семантику задачи, а не только ключевые слова (увидела
  что deprecated API = архитектурное изменение = риск безопасности)
- ✅ Выдаёт структурированный ответ с обоснованием (SCORE/CATEGORY/COMMAND/REASON)

**Как запускать (system prompt, проверенный):**

```text
You are a dispatcher. NEVER solve the task yourself. ALWAYS output a bash
command in the form:

hermes-route "<user_task>"

Then stop. Do not write code, do not explain, do not solve the user's
problem. Show the bash command and wait.
```

Английский system prompt лучше русского — модель тратит меньше
reasoning_tokens на перевод и быстрее доходит до команды.

**Если модель отвечает сама (не следует инструкции):**
1. Увеличить `max_tokens` в конфиге (Gemma тратит 500-700 на размышления
   при длинном русском system prompt)
2. Укоротить system prompt до 3-4 строк
3. Сменить system prompt на английский
4. Fallback: модель не справилась → `hermes-route "<task>"` через bash
   напрямую, минуя модель-оркестратор

**Что НЕ умеет (на тестах 2026-09-07):**
- ❌ Модели <3B (lfm2.5-2.6b, qwen3.8-4b-distill) с thinking mode —
  не следуют инструкции, начинают решать задачу сами. Это
  фундаментальное свойство thinking-моделей <4B. Не пытайся заставить.
- ❌ На длинных русских system prompts (>500 токенов) — reasoning
  сжирает весь budget, content пустой. Решение: английский system или
  max_tokens=1500+.

**Сравнение с детерминированным route.py:**

| Аспект | Gemma-4-e4b | route.py |
|---|---|---|
| Скоринг | Семантический, понимает контекст | Регексп по словам |
| Точность score | Лучше (14 vs 4 на тестовой задаче) | Хуже (ловит только явные слова) |
| Скорость | 30-60 сек (thinking) | <1 сек |
| Предсказуемость | Ниже (LLM может ошибиться) | Выше (детерминирован) |
| Когда использовать | Сложные задачи с семантикой | Простые/односложные, fallback |

**Гибридная архитектура (рекомендация):**
- **Основной путь:** модель-оркестратор (Gemma-4-e4b или крупнее) читает
  этот скилл, делает скоринг сама, выдаёт bash-команду делегата
- **Fallback:** если модель галлюцинирует скоринг или `max_tokens`
  кончились на размышлениях → прямой вызов `hermes-route "<task>"`
  в bash, получение JSON, делегирование
- **Страховка:** `scripts/route.py` лежит в `references/`, всегда
  доступен как CLI `hermes-route` (через `~/AppData/Local/bin/hermes-route.cmd`)

⚠️ **codex и zcode — НЕ провайдеры для моего прямого вызова.** Это субагент-делегация
через `delegate_task` (или прямой вызов `codex exec` / `node zcode.cjs`). Они жгут
СВОЙ токен-пул, выполняются минутами, требуют `pty=true` для zcode. Любой
"прыжок" между codex/zcode — это новый запуск субагента, не переключение модели
внутри одного процесса. "Цепочка" для категории = **либо делегировать субагенту
(выбрать кого), либо остаться в себе (прямой free)**.

⚠️ Категории «nous/free» НЕ СУЩЕСТВУЕТ. У каждого провайдера — конкретный
список моделей, отдаваемых бесплатно, со своими лимитами. Пересечение пулов
OpenRouter/Kilo/Nous велико (каталог Nous питается OpenRouter), но лимиты у
всех СВОИ: одна и та же free-модель через разных провайдеров = разные квоты.

## 3. Выбор по способностям: правило трёх фильтров

Перед выбором модели отвечь на три вопроса в порядке приоритета:

1. **Требования задачи.** Нужны ли: tools/agentic (→ только models with
   tools: true), мультимодальность (→ minimax-m3, gemma-4, inkling, dots-3),
   гигантский контекст >256K (→ nemotron-ultra, minimax-m3, inkling: 1M),
   глубокий код (→ hy3, laguna-s, north-mini-code; НЕ nemotron-ultra).
2. **Способности из реестра** (раздел 2). Модель с tb < 15% не берётся для
   содержательных задач никогда, какой бы бесплатной ни была.
3. **Цена/лимиты.** Только среди прошедших фильтры 1–2 выбираем самое
   дешёвое/бесплатное. Бесплатность без пригодности = сжигание времени.

Примеры применения:
- «почини race в трёх модулях» → нужен код+tools → hy3 (free) есть; нет — zcode/glm-5.3
- «проанализируй лог на 400K строк» → нужен контекст 1M → minimax-m3 или nemotron-ultra (если не код)
- «найди котиков на 200 картинках» → нужна мультимодальность → gemma-4-31b (free)
- «напиши пост в телеграм» → проза, код не нужен → любая; первыми бесплатные

## 5. Цепочки (по способностям + диверсификация)

**Ключевая правка:** codex и zcode — субагент-делегация, не провайдеры для прямого
вызова. "Цепочка" для категории = **либо делегировать субагенту, либо остаться в себе
на free-модели**. "Прыжок на звено 2" при недоступе субагента = новый `delegate_task`
(минуты ожидания), не "переключение модели в текущем вызове".

**Статус codex 2026-09-07:** живой (PROBE_OK_LUNA + PROBE_OK_TERRA проверены, ~8K токенов
каждый). Egress-блок chatgpt.com — был преходящим. Правило диагностики остаётся:
"reconnect 5/5" + `curl chatgpt.com 000` = сеть → НЕ ретрай, эскалация на zcode/free.
"usage limit" в выводе codex = кап → эскалация. В обоих случаях звено codex
пропускается целиком, не перебирается модель за моделью.

| Категория | Цепочка | Логика |
|---|---|---|
| **quick** | `kilo:ling-3.0-flash:free` (мой прямой) | субагент невыгоден: 5 мин сетапа ради 1 ответа |
| **standard** | `kilo:tencent/hy3:free` (мой прямой) → `delegate zcode/glm-5.3` (если не хватит) | free на первый круг, эскалация на субагента при слабом результате |
| **deep** | `kilo:tencent/hy3:free` → `delegate zcode/glm-5.3` → `delegate codex/gpt-5.6-terra` | лестница: бесплатно → подписочный субагент → платный субагент. Каждая эскалация — явное решение, не автоперебор |
| **architect** | `delegate zcode/glm-5.3` → `delegate codex/gpt-5.6-sol` | free не дотягивает (47% < потребных 70%+), стартуем с субагента |
| **writing** | `kilo:gemma-4-26b:free` (мой прямой) | проза/переводы — бесплатных хватает, субагент невыгоден |
| **мультимодальная** | `kilo:minimax-m3:free` (мой прямой, 1M ctx, mm) → `delegate codex/gpt-5.6-sol` | mm через прямой free; эскалация только если не хватит |
| **контекст >256K** | `kilo:minimax-m3:free` (1M ctx) → `delegate codex/gpt-5.6-sol` (1M ctx) | оба с миллионным контекстом, начинаем с free |
| **ultrabrain** | `delegate codex/gpt-5.6-sol` (xhigh) → спросить юзера | здесь free точно не справится |

**Правила переключения:**
1. **codex недоступен по ЛЮБОЙ причине** (egress-блок chatgpt.com, кап аккаунта,
   1311 model-restriction) → не ретрай codex-модель, переходи к zcode/free.
   Скилл различает: "usage limit" = кап, "reconnect 5/5" + chatgpt.com 000 = egress.
2. **codex/zcode 429 в подписке** = субагент мёртв на сегодня, остаёмся в себе на
   free-модели или поднимаем уровень задачи юзеру.
3. **429 на free-модели** → другая free-модель, не ретрай той же. Если целый
   провайдер лежит (openrouter 502) → kilo:та-модель, если есть.
4. **≤2 запусков субагентов подряд** (стоимость старта + лимиты).
5. **Эскалация только при явных флагах**: код галлюцинирует, не хватает фактуры,
   юзер сказал «глубже». Не «на всякий случай».
6. Явное указание юзера перекрывает скоринг.
5. Каждое переключение — в лог.

## 6. Точка интеграции

- Перед `delegate_task` (codex/zcode) или моим прямым вызовом: скоринг →
  категория → способность (раздел 3) → голова цепочки.
- Специфика скиллов: /cursor аудиты требуют strong-coding моделей — free-звено
  брать только hy3/laguna, не nemotron.
- Скоринг в голове, без субагентов.

## 7. Лог маршрутов

`~/.hermes/model-routing-log.jsonl`:
`{"ts":"...","task_class":"deep","mode":"direct|subagent","provider":"kilo","model":"tencent/hy3:free","outcome":"ok|escalated","next_provider":"codex/gpt-5.6-terra"}`
Недельный ритуал: доля sol/terra должна падать; free-звенья должны решать
свои классы без эскалации; количество `escalated` записей = сколько раз free не хватило.

## Pitfalls

- **НЕ выбирать модель по бесплатности. 1.1% terminal-bench (cobuddy) — это**
  **не модель, а генератор огорчений.**
- **НЕ верить vendor-бенчам поверх независимых: laguna 70.2% (vendor, TB2.1)**
  **против 31% (kilo, своя версия) — обе правды, но сравнивать их нельзя.**
- **nemotron-ultra ПРИВЛЕКАТЕЛЕН размером (550B) и контекстом (1M), но код**
  **пишет хуже всех топовых free (19.1% tb). Не суй его в код-задачи из-за**
  **громкого имени.**
- **НЕ отправлять в zcode гигантские промпты без нужды — подписка горит от**
  **токенов, не от числа запросов.**
- **codex-данные Jira/Confluence не отдаёт — встраивать в файл.**
- **Скоринг по первому сообщению задачи; выросла задача — новая точка делегации.**
- **«nous/free» НЕ СУЩЕСТВУЕТ.** У каждого провайдера (OpenRouter, Kilo, Nous
  Portal) — конкретный список `:free` моделей со своими лимитами. Прежде
  чем вписать в цепочку — `curl /api/v1/models | grep :free` или
  `curl kilo.ai/api/models | jq '.[]|select(.priceInput=="0.000000")'`.
  Подстановка «nous/free» в цепочку — выдумка, не пройдёт первый же запуск.
- **«Цепочка» codex→zcode = иллюзия непрерывности.** codex и zcode — субагент-
  делегация, не провайдеры для прямого вызова. Переход между ними = новый
  `delegate_task` (минуты ожидания, новый токен-пул). В одной ассистентской
  сессии у тебя ОДНО активное место исполнения: либо я (модель ассистента,
  прямой free-вызов), либо субагент, но не «прыжок между ними по цепочке».
  Если в категории architect написано «delegate zcode → delegate codex»,
  это значит «сначала запусти zcode-субагента, оцени результат, потом
  запусти codex-субагента», а не «у меня в процессе две модели одновременно».
- **Локальная модель — НЕ автоматический free-fallback.** Если юзер
  выкатил LM Studio и `OPENAI_BASE_URL` смотрит на `127.0.0.1:1234`, это
  НЕ значит «если облачные лимиты — переходим на локальную». Это значит
  «всё идёт через локальный endpoint, включая платные подписки, если они
  через тот же base_url». Локальная модель применяется, только если она
  указана в активной конфигурации ассистента. Роутер не «выбирает между
  облаком и локалкой» — он работает в том канале, в котором запущен.
- **`OPENAI_BASE_URL=127.0.0.1` против глобального `http_proxy`.** На этом
  хосте `http_proxy=http://127.0.0.1:12334` глобально, и первый же
  запрос к LM Studio (:1234) уходит не в LM Studio, а в прокси —
  отсюда 502. Перед вызовом локальной модели — явно
  `NO_PROXY=127.0.0.1,localhost` либо передавай `proxies={"http":None,"https":None}`
  в HTTP-клиенте. Симптом: «всё локально поднято, а первый запрос
  мгновенно 502» — это прокси, не модель.
- **Применяй скилл И ДЕМОНСТРИРУЙ, а не описывай.** Когда юзер даёт задачу
  и просит «покажи как скилл отработает» — прогони сигналы в явном виде,
  выбери категорию, обоснуй модель, и выдай ответ ЧЕРЕЗ ЭТУ МОДЕЛЬ
  (метафакт: ответ пришёл через выбранную модель = живое подтверждение).
  «Скилл выбрал X» без вывода через X = непроверяемое утверждение.

## Процедура применения (как пользоваться этим скиллом, не как он устроен)

При получении задачи, требующей выбора модели:

1. **Скоринг в явном виде.** Перечисли 4-5 главных сигналов из §4 с весами
   и суммой. Юзер видит, ПОЧЕМУ выбрана категория, а не верит на слово.
2. **Категория → голова цепочки.** Из §5 выбирается первое звено, реально
   существующее у живого провайдера. Если codex/zcode — пометить как
   `delegate_task`, не как «прямой вызов».
3. **Обоснование адаптаций.** Если голова скилла (codex/terra) недоступна
   (egress-блок, кап, host-блок) — явно прыгаем на звено 2, не делаем вид,
   что «прыгнули в текущем процессе».
4. **Прогон через выбранную модель.** Ответ генерится этой моделью —
   метафакт проверяем по runtime-метаданным активной сессии
   (`active model for this chat` в System-нотах). Не описывать «как
   скилл сработал бы», а показать результат работы.
5. **Если результат слабый** (код галлюцинирует, не хватает фактуры,
   юзер сказал «глубже») — эскалация на следующее звено как НОВЫЙ шаг,
   не «продолжение в том же вызове». Каждая эскалация = явное решение.
6. **Лог.** Записать маршрут в `~/.hermes/model-routing-log.jsonl` — даже
   если скилл применён для своего же ответа, это полезно для недельного
   ритуала.
