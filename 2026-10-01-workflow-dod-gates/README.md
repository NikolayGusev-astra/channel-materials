# Воркфлоу с DoD и гейтами на Hermes Agent

Материалы к статье «Воркфлоу с DoD и гейтами на Hermes Agent: 4 слоя, один прогон, ноль запретов в промпте».

## Что внутри

- `article.md` — текст статьи, источник истины
- `public/onto_gate.py` — клиент MemoryArtifact для Онто: `draft → submit → status → accept → supersede`
- `public/publish-draft.py` — публикация черновика на Telegra.ph с проверкой лимита заголовка

## Настройка

Оба скрипта читают секреты из переменных окружения и не содержат ни одного ключа.

```bash
export ONTONET_API_KEY=...            # токен вашего realm
export ONTONET_REALM=...             # UUID вашего realm
export ONTONET_MCP=https://app.ontonet.ru/mcp   # необязательно, это значение по умолчанию
```

Для Telegra.ph:

```bash
export TELEGRAPH_ACCESS_TOKEN=...     # либо TELEGRAPH_TOKEN в ~/.hermes/.env
export SOCKS=host:port               # необязательно, пусто = прямое соединение
```

`ONTONET_REALM` обязателен: без него скрипт падает с внятным сообщением, а не уходит в сеть с чужим realm.

## Использование

```bash
# создать артефакт с критерием готовности
python onto_gate.py draft \
  --path draw/2026-10-01-cover \
  --summary "1024x640, vision 4/4" \
  --dod-json '{"checks":["file exists","width==1024","vision 4/4"]}'

# предложить шаг на проверку
python onto_gate.py submit --path draw/2026-10-01-cover

# прочитать статус и аудит
python onto_gate.py status --path draw/2026-10-01-cover
python onto_gate.py audit  --path draw/2026-10-01-cover
```

## Граница, которую держит сервер

Гейт `proposed → accepted` держится не текстом инструкции, а правами токена. Скрипту на запись отдайте ключ с ролью, которая не может принимать решения, а право принятия оставь за отдельным ключом. Тогда шаг нельзя закрыть тем же ключом, который его создал, и никакая формулировка промпта это не изменит.

Токен, которым можно и создать, и принять артефакт, показывает только одно: у этого токена достаточно прав. Это не делает проверку на сервере бесполезной, но и не говорит о ней ничего — матрицу «роль → операция» стоит проверить на своих ключах.

## Известные особенности контракта

- `artifact_kind` — свободная строка в OpenAPI, реальный список сервер называет в тексте ошибки: `capability_dossier`, `decision`, `handoff`, `operation_matrix`, `review_log`, `review_protocol`, `test_strategy`, `worklog`
- `write_mode`: `replace` для `decision` и `capability_dossier`, `append` для остальных
- `targets` непустой, `target_kind` из списка `realm`, `template`, `entity`, `diagram`
- тело уходит ASCII-экранированным JSON
- поиск возвращает только принятые артефакты, поэтому идентификатор артефакта скрипт хранит локально — иначе шаг не пережил бы перезапуск
- отдельного инструмента аудита нет, события и счётчик записей лежат на самом артефакте

## Проверка на утечку

Перед публикацией страница проверяется запросом к API, а не чтением локального файла. Гейт ловит
не перечисление внутренних имён, а форму: любой UUID в опубликованном DOM считается утечкой,
потому что перечисление имён никогда не покрывает идентификаторы. Один такой UUID от рабочего
realm прошёл проверку «на список имён» и уехал в публичную страницу вместе с примером кода.
